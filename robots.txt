# Achievers Gospel Chapel — Static Site (Netlify + Supabase)

This is a fully static site (HTML/CSS/JS). There is no Node.js server, no
admin panel, and no login system. Content lives in Supabase and is read
directly from the browser using the public "anon" key. Content is edited
using Supabase's own dashboard — its Table Editor (for text) and Storage
(for images) — not a custom admin panel.

## 1. Create your Supabase project
1. Go to https://supabase.com → New Project (free tier is fine).
2. Once it's created, open the **SQL Editor** and paste in the entire
   contents of `supabase-schema.sql` from this folder, then run it.
   This creates every table, turns on Row Level Security with
   **read-only** access for everyone, and loads your real content
   (elders, ministers, choir leaders, programs, gallery categories,
   etc.) so you're not starting from a blank site.
3. Go to **Project Settings → API** and copy:
   - **Project URL**
   - **anon public** key

## 2. Connect the site to your project
Open `js/supabase-client.js` and replace the two placeholder values with
what you copied above:

```js
const SUPABASE_URL = 'https://xxxxxxxx.supabase.co';
const SUPABASE_ANON_KEY = 'eyJhbGciOi...';
```

The anon key is safe to publish — Row Level Security means it can only
ever *read* data, never write, regardless of what's in the JavaScript.

## 3. Deploy to Netlify
- Drag this whole folder onto https://app.netlify.com/drop, **or**
- Push it to a GitHub repo and connect it in Netlify (Build command:
  none needed — this is already static. Publish directory: the project
  root).

That's it — no environment variables, no build step, no backend to host.

## 4. How to edit content
Everything happens in the Supabase dashboard:
- **Text content** (settings, programs, events, sermons, elders,
  testimonies, announcements, etc.) → **Table Editor**, click into the
  relevant table, edit the row, save.
- **Images** → **Storage**, upload a file to a bucket (make the bucket
  public), then copy its public URL and paste that URL into the
  relevant table's `image_url` (or `site_logo`, `dept_img_*`, etc. in
  `website_settings`) field.
- **Colors/theme** → edit the `theme_mauve`, `theme_gold`, etc. rows in
  `website_settings` (must be a 6-digit hex code like `#9B7B9E`).
- **Testimonies** → new public submissions arrive by email (see below,
  they are NOT auto-saved to the database). To publish one, add a row
  yourself in the `testimonies` table with `approved` set to `true`.

## 5. What happens to the public forms now
There is no backend left to receive form submissions into a database or
an admin inbox. Every form (Contact, Prayer Request, Plan a Visit,
Department/Ministry sign-up, Event Registration, Testimony) now submits
**directly to Formspree** from the visitor's browser. The church still
receives every submission by email; it just won't show up anywhere in
Supabase or in a dashboard.

The Formspree endpoint is set in `js/main.js`:
```js
const FORMSPREE_ENDPOINT = 'https://formspree.io/f/xykqdwow';
```
Replace this with your own Formspree form ID if this one isn't yours.
Log into Formspree and confirm the form is verified for your domain —
first-time/unverified submissions are sometimes blocked.

## 6. What was intentionally left out of this version
Compared to the previous Node/Postgres/admin-panel version, this static
build does **not** include:
- An admin dashboard (content is edited directly in Supabase instead)
- File upload from a custom UI (use Supabase Storage's own uploader)
- A database record of form submissions (they go to email only now)
- A moderation queue for testimonies (approve by editing the row directly)
- User accounts / login of any kind

## 7. Cleaning up the old database (optional, do this last)
If you were previously running the Node/Postgres version and are fully
done with it, `OPTIONAL-drop-old-database-tables.sql` is provided
separately to remove the admin/session/submission tables from **that**
old database. It is not run automatically, it has nothing to do with
Supabase, and it permanently deletes any contact messages, prayer
requests, visit requests, department applications, and event
registrations still sitting in that old database. Read it before running
it. Only run it against the old database, and only when you're sure.
